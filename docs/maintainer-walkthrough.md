# Maintainer walkthrough

Start in `scripts/demo.ts`. It creates an application per mode, creates synthetic orders through a local harness, invokes the engine with explicit plans and checks actual report outcomes. Expected broken failures are assertions made by the parent suite, not disabled test cases. Each handle's finally block removes its owned resources.

1. `src/engine/config.ts` validates before sending. `network.ts` validates origins/IPs, resolves DNS at connection time and pins a validated address. It bounds request duration/response bytes and follows no redirects. `index.ts` signs raw JSON bytes, records each bounded attempt, and then polls executable business assertions. HTTP200 and fulfilment count are distinct evidence.
2. `src/sample/index.ts` is ingress. It checks raw-byte HMAC, shape, order, amount and currency before recording corrected inbox+job atomically. One inbox event ID cannot silently change identity. Broken mode deliberately omits business deduplication.
3. `src/sample/worker.ts` is the transaction boundary: select/lock job; lock order; write fulfilment and paid state; mark job done; commit. A unique per-order constraint is a second defence against distinct successful event IDs for the same order. This is a local database guarantee, not proof of exactly-once external effects.
4. The race test sends10 concurrent deliveries, then reads persisted business state. It also tests distinct valid identities/orders; a global boolean deduplicator would fail that test. No in-memory process flag establishes correctness.
5. The timeout fault waits for a durable business change and intentionally withholds acknowledgement. The runner times out and retries; broken count becomes2, corrected count stays1. The report records both attempts and the separately observed count.
6. IPC checkpoints pause only the owned child before or after COMMIT. The harness confirms the signal, sends SIGKILL, restarts against the same tables and inspects state. Before commit, PostgreSQL rolls back the interrupted transaction; after commit, the completion survives. There is no remote kill endpoint.
7. `examples/external/server.ts` independently stores state in a disposable JSON file and exposes a read-only adapter. This demonstrates the HTTP integration contract without sharing the PostgreSQL sample implementation. Its file/mutex guarantees are intentionally narrower.
8. `src/report/index.ts` whitelists exports and escapes all content. A partial or contradictory passing report becomes an execution error; JSON/HTML/JUnit must agree. Static reports need no backend and can be transferred to a phone.

Tradeoffs: a database table over a queue service, explicit schedules over nondeterministic random generation, declarative HTTP assertions over executable plugins, static reports over a hosted app. See ADR001 for alternatives. Background work outside the observation window remains a limitation: use a terminal application completion status and an adequate stable window.
